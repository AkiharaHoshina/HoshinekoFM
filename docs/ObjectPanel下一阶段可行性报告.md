**贯穿全过程的用户原则**（后续阶段应继续遵守）：

1. **拖拽只导航/固定，绝不操作**——对象拖到标签页 = 打开、拖到终端 = cd、拖到固定区 = 投影；终止/写入类危险动作永不进拖放。
2. **落点语义与文件夹拖放对齐**——文件夹能「移动/复制进去」的落点（已固定条目），对象无此语义则**不予接受、无反应**。
3. **授权模型统一**——需要提权的操作一律「先解锁再拖」，一次授权、本会话有效、状态常驻可见。
4. **反馈明确**——成功 toast、常驻状态提示、错误按码翻译（12 语言）。

**你的明确取舍**：

- 「不能调高优先级就全部锁定、先解锁再拖」——授权成本前置、拖动方向不可预判时的确定性优先于免授权便利。
- 「落错地方要没反应」——宁可少落点，不可误导（对象拖到已固定文件夹上不允许「移动进去」的假象）。
- 交互细节反复打磨（提示第二行、解锁后常驻状态、触发区大小）——**交互一致性高于功能数量**。

## 二、我的思路补充（按主题，附价值/风险/工作量评估）

### 2.1 对象动作纵深：从「看」到「管」（价值 ★★★）

对象面板目前是「监控 + 少数写动作」。下一步最有价值的纵深是**多对象批量与关系**：

| 候选 | 说明 | 价值 | 风险 | 工作量 |
| --- | --- | --- | --- | --- |
| **进程树视图** | 按 ppid 层级折叠展示（如 htop 树模式）；与现有虚拟化列表共存可切换 | 高——进程关系是当前列表平铺最大的信息缺口 | 低（只读 /proc） | 中（树形虚拟化 + 折叠态） |
| **批量进程操作** | 多选（Ctrl/Shift）→ 批量 TERM/批量调 nice；确认对话框同现有 L2 语义 | 高——一次关掉一组僵尸进程是高频需求 | 中（误伤面大，须确认 + 上限） | 中 |
| **性能模式切换** | power-profiles-daemon（性能/平衡/节能），读写 `org.freedesktop.UPower.PowerProfiles` 或 CLI | 中——笔记本刚需 | 低 | 小 |
| **充电阈值** | 写 `/sys/class/power_supply/BAT*/charge_control_end_threshold`（root 644） | 中——与「先解锁再拖」模型天然契合（复用写通道 + 助手） | 低 | 小 |

## 四、建议路线图（讨论后拆分）

1. **近期（本阶段）**：解锁撤销 + 进程树/批量操作 + 告警徽标——「面板既能看也能管，且授权可收回」。
2. **中期**：性能模式 + 充电阈值（复用解锁模型）+ 投影闭环（重命名/快捷键/互拖）+ 搜索命中高亮。
3. **远期**：OS 级拖出、管理员模式、走势图持久化、迷你悬浮窗——各成独立可行性报告再动工。

**待讨论的开放问题**：

1. 批量进程操作的确认语义：一次确认覆盖全部，还是逐进程确认？建议「一次确认 + 结果汇总 toast」。
2. 解锁自动锁定：是否引入「失焦 N 分钟自动锁定」？还是只做手动「重新锁定」？
3. 充电阈值是否值得进（厂商硬件支持差异大，部分设备写无效）？建议做成「检测到支持才显示」（SMART 同款哲学）。
4. 进程树视图与现有虚拟化列表的关系：并存切换 or 替换？建议并存（树模式切换按钮）。
5. 下一阶段范围拍板：P0 三项是否够「一阶段」？
